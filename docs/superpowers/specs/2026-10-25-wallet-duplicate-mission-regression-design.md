# HPA-421 — Duplicate Wallet Settlement Mission Regression: Design

**Linear:** [HPA-421](https://linear.app/cwchanap/issue/HPA-421/regression-duplicate-wallet-settlements-must-not-double-count-missions)  
**Status:** Design proposal; no runtime change or new persistence  
**Delivery:** One PR for design, tests, and any proven fix

## Context and code-verified findings

The original issue described a double-count race in `/api/chips/update`, gated by a receipt's existence rather than by the current transaction's winning attempt. That endpoint and `chip_sync_receipt` were removed in HPA-545.

Today:
- `src/lib/wallet/repository.ts:applyWalletSettlementBatch` executes a guarded balance UPDATE, conditional `wallet_settlement` INSERT, `game_stats` UPSERT, and mission-progress statements in one `d1.batch`.
- `wallet_settlement` has a unique `(userId, settlementId)` key and a server-only `attemptId`; the latter is generated by `src/lib/wallet/settle.ts` for each attempted settlement.
- Both `WALLET_STATS_UPSERT_SQL` and `src/lib/missions/progress.ts:buildReceiptGateSql` require `(userId, settlementId, attemptId)` to match the receipt. A duplicate that sees the winning receipt but has a different attempt ID must not apply effects.
- `UPDATE user` also checks `NOT EXISTS(wallet_settlement)`, protecting zero-delta replays where `chipBalance` alone cannot distinguish a duplicate.
- `src/lib/wallet/repository.test.ts` uses a real in-memory Bun SQLite engine behind the D1 interface and covers fresh settlements, stale expected balances, and a duplicate push that checks stats. It does not directly assert that a duplicate replay leaves mission progress untouched.

The previous suggestion to add `mission_sync_ledger` is **not** justified by the current code. The existing attempt-ID gate is the intended protection. This ticket closes a focused regression-proof gap; it is not a new wallet architecture project.

## Goal

Prove with executable real-SQL repository tests that **one logical settlement advances the wallet, statistics, and relevant mission progress at most once**, even when the same settlement ID is submitted with a different server attempt ID after the winner has committed.

## Expected behavior / acceptance

1. **First settlement wins:** a Blackjack win for one new test user applies successfully, creates one receipt, and advances `game_stats`, `daily-blackjack-5`, and `daily-win-3` exactly once.
2. **Duplicate replay loses:** reapply that same `settlementId` with a different `attemptId`. It returns `false`, preserves the original receipt and wallet balance, and does not increment `game_stats` or either mission.
3. **Unchanged-balance duplicate loses:** a fresh zero-delta Blackjack push advances its `handsPlayed` mission once; replay with the same settlement ID but a new attempt ID leaves balance, stats, and `daily-blackjack-5` unchanged. This exercises the zero-delta special case.
4. **New event still works:** a distinct settlement ID with an appropriate expected balance applies normally and advances progress, avoiding a regression that blocks all later events.
5. All assertions run against the **actual prepared SQL and transaction ordering**, not a mock that pretends the receipt EXISTS predicate works.
6. No new schema, ledger, endpoint, cross-tab coordination, art/SFX, or generalized concurrency harness.

## Implementation boundary

**Preferred file:** `src/lib/wallet/repository.test.ts` only. Reuse `createDatabase`, `insertUser`, `command`, `readWalletBalance`, `readGameStats`, and `findWalletSettlement`. Add a tiny local progress-row query or helper if needed; use distinct user IDs to keep the shared test database isolated.

Avoid a wall-clock-dependent period assertion: look up the mission by `userId` and its unique test mission ID, as existing repository tests already do; only use a period-key assertion if it makes the case clearer and stable.

If a new test fails on current `main`, inspect and fix the minimal demonstrated problem inside the **same PR**, then re-run the test. Do **not** implement the historical ledger idea merely because it appears in the archived issue description.

## Out of scope

- Retesting actual parallel Cloudflare network requests when a sequential committed-winner/loser case captures the historical race condition.
- Adding Miniflare infrastructure solely for this test; current Bun SQLite harness executes the SQL.
- Revising guest bankroll, achievement notifications, ranked/daily Blackjack, or wallet retry UX.
- Refactoring public wallet APIs, adding dependencies, schema changes, or backwards-compatibility layers.

## Review decision

**Ship as a narrow regression test, not a production rewrite.** The code already carries the core correctness mechanism; a test that fails when the attempt-ID gate is accidentally weakened provides useful protection at much lower cost.
