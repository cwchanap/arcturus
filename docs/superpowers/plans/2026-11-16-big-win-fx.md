## Steps

### 1. Generate and optimize the five WebPs

- [ ] Use the ticket's Codex-on-Mac image-generation setup (`gpt-6-luna`, `xhigh`) and `public/images/poker/` references. Make one top-down single gold-chip master; recolor/repaint red and blue with exactly the same shape, bevel, padding and viewpoint. Generate one glint sprite.
- [ ] Generate a transparent Art Deco ribbon with **at least ~55% of width and height reserved as a quiet center band**, suitable for stacked localized title + chip counter. Favor **960 × 280–320** over 960 × 240 if needed for a 375px phone. Keep corners truly transparent, and no baked text.
- [ ] Export four **128 × 128** WebPs and one ~960px-wide ribbon into a temporary staging directory. Optimize all images toward **~100 KB total** without destroying alpha/quality. Test particles at 24/32/48 CSS px. Measure and record the exported ribbon's real `(x, y, width, height)` safe-area coordinates.

### 2. Generate and level the two MP3s

- [ ] Use ElevenLabs on the Mac for `coin-shower` (~1.5 s) and an original `big-win-sting` (~2 s); no speech, recognizable melody or long reverb tail. Export final **mono 44.1 kHz MP3s**, **≤100 KB each**.
- [ ] Measure the final decoded clips with `ffprobe` and `ffmpeg -af volumedetect`. For any adjustment, use **fixed gain** (`-af volume=<dB>dB`), not one-pass `loudnorm`: short transient SFX should keep their dynamics. Re-measure **after MP3 encode**.
- [ ] Mix the final decoded shower and sting **starting together** using `amix=inputs=2:duration=longest:normalize=0`, then measure **true peak** (e.g. `ebur128=peak=true`). Target **≤−1 dBTP** for the composite, reducing gains if necessary; isolated ~−6 dBTP is a starting point, not proof the sum is safe. Verify decoded clean starts/ends and no clipping; macOS `afinfo`/`afplay` can aid a local audition. The existing synthesized poker `bigWin` cue can be compared in the running game, **without building an ephemeral JS bundle**.

### 3. Inspect files and run **one** scratch visual preview

- [ ] Run **`webpinfo` plus Pillow from `/opt/homebrew/bin/python3`** where available (or equivalent already installed tools), not ImageMagick assumed to be installed. Check dimensions, WebP encoding, actual alpha at outside pixels, visual framing, bytes per image/total. For audio use `ffprobe`, `ffmpeg`, `afinfo` to confirm codec, sample rate, channel count, duration, final peaks and bytes. Do not add validation scripts/dependencies to the repository.
- [ ] Build **one plain static HTML file outside Git** referencing staged images and `public/images/poker/felt.webp`. Render chips at native and 24/32/48px, sparkle, and ribbon with **two stacked HTML lines for each of `en`, `zh-Hant`, `zh-Hans` and `ja`**. No JS bundle, no audio player, and no second Astro preview; a tiny temporary static server is fine if `file://` cannot load the files.
- [ ] **Browser MCP E2E (one platform):** open this scratch HTML, capture **1280 × 800** desktop and **375 × 812** phone-viewport screenshots, and visually check chip distinction/alpha, table-style match, ribbon layout and all locale text inside the measured safe band. Record actual platform/browser and screenshot evidence. There is no Linear UI mockup, so this screenshot-based visual check is mandatory. **No headless-browser audio E2E or redundant HTTP 200 check**; audio already has decoder and waveform/peak checks.

### 4. Deliver a working preview before any binary commit

- [ ] Use the **Linear HPA-728 Resources** uploader, not GitHub issue-comment binary uploads. For **each** preview PNG, individual MP3 and (if useful) temporary layered-mix MP3: `prepare_attachment_upload` → upload exact raw file bytes with signed headers via PUT → `create_attachment_from_upload`. Prepare/upload/finalize one at a time because signed URLs expire quickly. These are preview attachments only, not repository assets.
- [ ] Post **one Linear HPA-728 comment** linking the uploaded screenshots and sound previews and identifying the required feedback. Post a concise **PR #89 Conversation comment** with the Linear issue/preview link, safe-area proposal and recorded measurements. The ticket requests a **go-ahead on that Linear preview before committing the seven binaries**; absent feedback, retain the staged files and keep the PR draft. Do not assume an MCP-generated screenshot constitutes the user's feedback. This approval step is a pre-commit workflow condition, **not an automated end-to-end test**.

### 5. Finalize on the existing draft branch

- [ ] After the preview checkpoint, copy only the **seven final files** to the exact paths from the spec. No new source code, generated preview, scripts or unrelated binaries.
- [ ] Run `bun run format:check` and `bun run build` locally and record results. The current GitHub workflow **skips lint and its dependent build on draft PRs**; do not label skipped CI as passed. Note that `docs/superpowers/` is listed in `.prettierignore`, so the format command does **not** validate these two planning files; review their Markdown directly.
- [ ] Update the PR description with the actual image size total, individual MP3 bytes/duration/sample rate, composite true peak, ribbon pixel safe-area, screenshot links/MCP environment and command outputs. Keep HPA-729 blocked until the final asset PR lands; then carry the existing poker `bigWin` synth-overlap warning into that implementation.

- [ ] **Visual E2E by browser MCP:** desktop and phone screenshots from the **single scratch preview** checked against the current felt/art direction; 24–48px chip legibility, no rectangular matte, ribbon's two-line four-locale overlay fitting within the measured text-safe rectangle.
