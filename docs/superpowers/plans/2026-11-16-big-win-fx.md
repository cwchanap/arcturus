# HPA-728 — Big-win celebration sprites and SFX: implementation plan

**Linear:** https://linear.app/cwchanap/issue/HPA-728/assets-big-win-celebration-sprites-and-sfx  
**Design:** [2026-11-16-big-win-fx-design.md](../specs/2026-11-16-big-win-fx-design.md)  
**PR contract:** **One draft PR for HPA-728**, including these planning docs and eventually all seven finalized assets. Do not open a separate implementation PR for this issue. The gameplay/animation work is **HPA-729**, its own separate ticket/PR, and remains blocked until this asset PR lands.

## Starting state and constraints

- Main already has painted 128 × 128 transparent poker chips in `public/images/poker/pot-chips.webp`, an Art Deco emblem, felt and card backs; match this style rather than creating a generic casino look.
- The ticket asks for **five WebP images** in `public/images/fx/` and **two MP3 files** in `public/audio/fx/`. None of the expected `chip-gold.webp` / `coin-shower.mp3` target paths currently exists on main.
- Source images, production prompt notes, big rendered intermediates, audio masters, and contact sheets should live **outside Git**. Commit only final assets plus the two plan documents.
- **No changes to `src/`, package dependencies, game pages, localization, HTML/CSS, database, or APIs.** Do not build a preview feature or celebration code to test the assets.
- The Linear ticket explicitly requests previews for approval before binary assets are committed. Preserve this ordering. It is **not** an acceptance criterion requiring human verification; automated evidence below is the technical completion gate.

## Implementation sequence

### 1. Paint and prepare the five images (assets only)

- [ ] Use Codex on the Mac with the ticket's requested image-generation setup (`gpt-6-luna`, `xhigh`) and existing `public/images/poker/` art as direct references. Generate a strong top-down gold-chip master, then derive matching red and blue variants using the **same shape, rim, highlights and padding**. If recoloring reduces readability, render a targeted variant instead; no custom asset-generation framework.
- [ ] Create one compact gold glint with clean transparent falloff, and one wide metallic Art Deco ribbon with clear central space for later HTML-overlaid localized text. **Never bake “Big Win”, currency amounts, icons with text, or locale-specific copy into the images.**
- [ ] Resize/optimize to the design contract: each chip and sparkle 128 × 128; banner ~960 px wide, nominal 960 × 240. Confirm real alpha, especially corners/outside shape, and readability at **24, 32 and 48 CSS px**.
- [ ] Export only final optimized WebP into a temporary staging folder. Tune WebP quality to bring **all five images together to roughly ≤100 KB**. Record per-file sizes and total. Preserve alpha and avoid obvious ringing on gold edges.
- [ ] Assemble a temporary preview sheet: chips at native size and actual animation size; sparkle on dark felt; ribbon with **temporary HTML text** over the current poker background. Capture desktop and phone-sized candidate screenshots. Share the sheet before committing generated assets as requested by Linear.

### 2. Generate and prepare the two sounds (assets only)

- [ ] Generate original sounds with ElevenLabs on the Mac: `coin-shower` (~1.5 seconds, light cascading chips) and `big-win-sting` (~2 seconds, tasteful short flourish). Avoid speech, copyrighted melody, long ambience and unnecessary music tracks.
- [ ] Edit length/tails and normalize modestly if necessary; export MP3 rather than relying on source WAV/OGG. Keep **each MP3 ≤100 KB**; check the actual decoded durations and whether playback reaches its end without a pop or clipping.
- [ ] Supply playable preview files alongside the contact sheet for the ticket's preview/approval step. Do not commit scratch WAV, reference audio, source generation files or preview page.

### 3. Add final assets to this same draft PR (after preview gate)

- [ ] Copy the final files into exactly these paths:
  - `public/images/fx/chip-gold.webp`
  - `public/images/fx/chip-red.webp`
  - `public/images/fx/chip-blue.webp`
  - `public/images/fx/sparkle.webp`
  - `public/images/fx/big-win-ribbon.webp`
  - `public/audio/fx/coin-shower.mp3`
  - `public/audio/fx/big-win-sting.mp3`
- [ ] Keep the existing branch and PR; **do not** create a second PR for binary assets. Do not edit HPA-729 files or add a mock integration layer. Ensure the final diff contains only the above seven files and the two documents.

### 4. Validate quality and delivery

- [ ] Run a one-off image metadata/alpha inspection (e.g. Pillow or ImageMagick) against all five final WebPs: dimensions, encoding, presence of an alpha channel, transparent outer pixels, filesize. Pay particular attention to ribbon alpha and consistent chip framing.
- [ ] Run `ffprobe` (or equivalent metadata tooling) for both MP3s: correct codec, duration (~1.5 s / ~2 s), file size ≤100 KB each. Verify browser decode and user-initiated audio playback; an automated check must confirm playback reaches `ended`, not just that the HTTP request succeeds.
- [ ] Run `bun run build` and `bun run format:check` from the final branch. No backend code is changed; do not add irrelevant database/backend E2E tests.
- [ ] **Browser MCP end-to-end**, on **one desktop browser platform** with phone viewport emulation:
  1. Start Astro locally; request all seven resources by their actual `/images/fx/...` and `/audio/fx/...` URLs and assert successful responses.
  2. In a **temporary, uncommitted** browser preview of the existing poker backdrop, programmatically load/decode all sprites and create a centered ribbon with temporary DOM text. At desktop **1280 × 800** and phone **375 × 812**, capture screenshots and inspect the styling, centering, edge transparency, 24–48 px legibility and ribbon fit.
  3. In the same browser session, use a click/user gesture to trigger both MP3s, asserting successful decode/playback and eventual `ended` with no console errors.
  4. Record which MCP/browser/OS ran, the asset sizes and durations, and links or paths to screenshots in the PR description. **Do not claim that a live gameplay win triggers the effects; that belongs to HPA-729.**
- [ ] After acceptance evidence passes, make a final audit that there are no implementation code changes and that HPA-729 can use each stable path without renaming.

## End-to-end acceptance criteria

- [ ] All **seven contract filenames** exist on the draft PR branch and return HTTP 200 through the built/served Astro site; all five images decode in-browser, all two MP3s decode and complete playback following a user gesture.
- [ ] Automated binary checks confirm four 128 × 128 WebP sprites, a ~960 px banner, true alpha/transparent edges, a total image budget around 100 KB, and two MP3s of the expected approximate lengths under 100 KB each. File sizes/durations are recorded.
- [ ] **MCP visual screenshot check:** 1280 × 800 desktop and 375 × 812 phone screenshots of the candidate preview over the existing table are inspected by the agent, because Linear has **no mockup**. Chips distinguishable at intended display sizes; glint and banner do not have matte boxes; gold/green Art Deco style matches the existing poker art; centered ribbon remains usable on phone.
- [ ] `bun run build` and `bun run format:check` pass; the PR diff includes exactly two documentation files and seven generated binaries, not application code or added dependencies.
- [ ] The PR includes actual verification evidence, screenshot references, and clear identification of the tested browser platform. One platform suffices because there is **no platform-specific implementation change**. Do not substitute manual sign-off for the MCP acceptance check.
- [ ] HPA-729 stays separately tracked and blocked on completion of HPA-728. No human-acceptance criterion is included.
