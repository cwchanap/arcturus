# HPA-731 — Chip shop and poker cosmetics: implementation plan

**Linear:** https://linear.app/cwchanap/issue/HPA-731/chip-shop-buy-and-equip-poker-table-cosmetics  
**Design:** [2026-11-21-chip-shop-cosmetics-design.md](../specs/2026-11-21-chip-shop-cosmetics-design.md)  
**Dependencies:** HPA-730 art assets already merged as [PR #95](https://github.com/cwchanap/arcturus/pull/95) into `main` (baseline `8e03a5e`).  
**PR discipline:** **Exactly one PR for this ticket.** This is a planning-only draft; commit implementation, tests, fixes and browser-MCP evidence to **this branch/PR**, not a separate implementation PR.

Keep this a small Astro/D1 feature. No new assets, packages, generic commerce layer, inventory database, currency system, old-schema compatibility, route refactor, or new game framework.

## 1. Catalog and schema

- [ ] Create `src/lib/shop/catalog.ts` with `SHOP_ITEM_IDS as const`, `ShopItemId` union, an exhaustive `Record<ShopItemId, ShopItem>` catalog, runtime ID validation and per-kind IDs/defaults (mirroring `src/lib/missions/types.ts`). Include the eight fixed items: 2 free defaults, 6 shipped HPA-730 WebPs, prices 5k/15k/40k per Sapphire/Crimson/Jade item. The catalog is the **sole price/image authority**.
- [ ] Add the `userCosmetic` Drizzle table in `src/db/schema.ts` with `(userId, itemId)` PK, user cascade delete, `purchasedAt` unix seconds and boolean `equipped`. Defaults remain implicit; no rows for them, no second kind/index/catalog table.
- [ ] **Hand-write `drizzle/0021_user_cosmetic.sql`** mirroring the Drizzle table, following `drizzle/0018_blackjack_run.sql`. Existing `drizzle/meta/*` snapshots are ignored/incomplete; `bun run db:generate` either fails with broken metadata or starts from `0000` and recreates old tables. Do not run the generator for this schema change, do not add generated metadata, and leave the `0019` prefix gap untouched. The migration runner already discovers numbered SQL; do not edit `package.json` or the Better Auth `user` table.
- [ ] Verify the migration applies with `bun run db:migrate:local` on a clean/local test DB.

## 2. Minimal shop service and transactional correctness

- [ ] Add focused `src/lib/shop/` functions for: reading owned/equipped state, purchasing a catalog item and equipping an owned/default item. Use `D1Database` directly where the two-statement `batch()` matters; do not wrap the entire wallet module or add a generalized repository hierarchy.
- [ ] Implement purchase with one bound `INSERT ... SELECT FROM user WHERE chipBalance >= price ON CONFLICT DO NOTHING` followed **immediately** by `UPDATE user SET chipBalance = chipBalance - price WHERE id = userId AND changes() = 1 RETURNING chipBalance` inside `d1.batch([...])`, as established by `src/lib/missions/claim.ts`. Take the successful post-debit balance from the second batch result's returned row; do not perform an extra success-path SELECT. On no insert, distinguish ownership from insufficient funds and reuse `readWalletBalance` from `src/lib/wallet/repository.ts` if the current balance is needed. Duplicate/insufficient requests never debit. Verify this result shape with real D1 integration tests.
- [ ] Accept only `{ itemId: string }` for equip; validate against the server catalog and **derive kind from the item** (no redundant `kind` payload). Equip an owned paid item with one SQL `CASE WHEN itemId = target THEN 1 ELSE 0 END` UPDATE over that kind's purchased IDs, guarded by an `EXISTS` ownership condition so an unowned target cannot clear a previous selection. Equipping a free default clears flags only for its kind. Return `{ kind, equippedItemId: itemId }` on success, with **no additional read of the other kind**. Do not alter the other kind; defaults are inferred when none is equipped.
- [ ] Keep server catalog validation strict: unknown item ID, unowned paid item, default purchase and invalid JSON cannot mutate DB. No redundant client kind or mismatched-kind validation is needed. No achievement, wallet settlement, game stats, or mission hooks for a purchase.
- [ ] Add thin authenticated endpoints `src/pages/api/shop/purchase.ts` and `src/pages/api/shop/equip.ts`. Validate untrusted item strings to the closed `ShopItemId` union, use `401 UNAUTHORIZED`, `400` for invalid/insufficient items, `403` for unowned, `409` for already-owned and **`500 DATABASE_UNAVAILABLE`** for missing D1. Return new balance for a purchase and `{ kind, equippedItemId }` for equip. No extra GET API: the shop page renders its initial state with Astro SSR.

**Concurrency invariant:** a double-click/two simultaneous POSTs buying the **same item** inserts at most one `user_cosmetic` row and subtracts its price once; two purchases of **different** items cannot overdraw the current user balance. Prove this at least in D1 integration tests, not just a mocked service.

## 3. Accessible shop UI and navigation

- [ ] Implement protected `src/pages/shop.astro` importing `CasinoLayout` from `src/layouts/casino.astro`; use existing `readWalletBalance(d1, userId)` for authoritative SSR balance and catalog/ownership helpers. Missing session redirects to `/signin`, absent DB responds with **503** as in `src/pages/missions/index.astro`. Add `Astro.response.headers.set('Cache-Control', 'private, no-store')` for this authenticated page, matching `src/pages/profile.astro`. The page has two sections, **Card Backs** and **Table Felts**, with four tile previews each (default, Sapphire, Crimson, Jade), prices, owned/equipped text, and Buy/Equip/Equipped controls.
- [ ] Reuse `deco-panel`/`deco-btn` typography and colors; use shipped WebPs directly at small displayed sizes. On purchase/equip, keep the smallest possible client script: disable pending button, `fetch` the existing API, update price/owned/selection and localized balance from responses, and show localized errors. Put `data-chip-balance` on the **shop page's visible balance span** as well as reusing the existing desktop `[data-chip-balance]` in `AppLayout.astro`; one `querySelectorAll('[data-chip-balance]')` loop with `formatChips` must update **both**. The shared header balance pill is `hidden md:block`, so only updating it leaves the phone shop showing a stale balance at `375×812`. On reload, SSR must agree with the rendered state.
- [ ] Add the shop entry link near existing actions in `src/pages/profile.astro` instead of adding another item to the crowded shared mobile header. Link back to Poker from the shop for an obvious way to inspect the result.
- [ ] Add one focused `src/lib/i18n/messages/shop.ts` dictionary for `en`, `zh-Hant`, `zh-Hans` and `ja` using existing `defineMessages`/`createTranslator` and `formatChips` conventions. Type each locale's item names exhaustively against `ShopItemId` so missing translations fail `astro check`. Buttons should announce the item's name/action; equipped state must not depend on color alone.
- [ ] Use responsive grid/tile sizing at `375×812` without horizontal scrolling or button overlap. Do not create images, animations, a new design-system layer or a separate mobile implementation.

## 4. Apply cosmetics through existing Poker SSR + CSS seams

- [ ] In `src/pages/games/poker.astro`, for authenticated users with D1, load effective felt and card-back paths via the shop registry and ownership rows; set `Astro.response.headers.set('Cache-Control', 'private, no-store')` for authenticated SSR as in the existing profile page. For guests, absent selections or a cosmetic read failure, retain the existing defaults.
- [ ] Set `--poker-felt-image` and `--poker-card-back-image` on shared `#poker-root` to **complete CSS URL values** (e.g. `url('/images/shop/felt-sapphire.webp')`), assembled only from known server catalog paths; omit each property's declaration for the default to activate the CSS fallback. **Bare file paths are not valid `background` image values, and `url(var(...))` is invalid.** Never interpolate arbitrary request-supplied CSS/URLs.
- [ ] In `src/styles/poker.css`, replace only the image portions of the existing `.poker-frame` felt background and `.poker-room .card-back-deco` background with CSS `var(...)` plus the current asset URL as fallback. Preserve the overlays/gradients, border, sizing, card-face rendering and UI readability.
- [ ] Test **both** `/games/poker` and `/games/poker?mode=sng`; they share the SSR template. Leave private-room multiplayer Poker and other card games unchanged.

## 5. Automated regression tests

- [ ] `src/lib/shop/catalog.test.ts`: the closed `ShopItemId` union and four locale name maps cover eight unique IDs; six nondefault image URLs exist in known locations; prices/kinds/default ownership are correct; lookup rejects unknown IDs and does not accept a client-supplied price. Verify that the Poker CSS variables receive **valid `url(...)` values** when paid, and are absent/fallback for free defaults.
- [ ] Focused Bun + actual D1/Miniflare integration tests (following `src/lib/missions/claim.test.ts`): affordable purchase debits once; duplicate and unaffordable purchases debit zero; two concurrent attempts for same item result in exactly one successful debit; concurrent different-item purchases never overdraw; exact boundary balance succeeds; unknown/default IDs fail; equip validates ownership/kind, replaces within a kind, keeps other kind, restores default, and remains after a fresh service read. Assert `changes()` behavior with the **real D1 batch**, not only mocks.
- [ ] Thin API route tests for authentication, invalid JSON, equip's `{ itemId }` contract / `403 NOT_OWNED`, and `500 DATABASE_UNAVAILABLE` responses; follow `createPostHandler` dependency injection in `src/pages/api/wallet/settle.ts` / `src/lib/wallet/settle-api.test.ts` rather than inventing another HTTP test harness.
- [ ] Create `e2e/shop.spec.ts` using `createIsolatedPage` (never the shared auth user for wallet-mutating tests). With a new 10,000-chip user: buy Sapphire card back (5,000 remaining), reject repeat and Jade, buy Sapphire felt (0 remaining), equip both using `{ itemId }`, and refresh shop. Assert that both the shop-visible **mobile** balance and the desktop header `[data-chip-balance]` show the updated values, plus `private, no-store` on authenticated `/shop` and Poker. **Cash Poker at 0 chips cannot deal:** assert the selected felt visually and card-back URL via `getComputedStyle` on the hidden `.card-back-deco`. In solo Sit & Go, the independent tournament stack permits a hand; assert a **visible** card back and the felt. Restore both defaults and verify CSS fallback URLs after reload. Add a second isolated user to verify no inventory leakage; reject unauthenticated API attempts. Use bounded assertions and no arbitrary sleeps.
- [ ] Keep the E2E test deterministic: the two affordable 5,000-chip Sapphire items are sufficient for both kinds. Do not add a production debug balance endpoint, new seed system, RNG manipulation or manual test precondition.

## End-to-end acceptance criteria

- [ ] An authenticated user can purchase affordable items once, with one conditional transactional debit using the **current** D1 balance and post-debit `RETURNING chipBalance`; repeated/parallel purchases and insufficient-funds requests cannot double-charge, grant free ownership or go negative. Real D1 integration tests plus Playwright prove the failure/concurrency cases, while browser MCP proves the connected happy-path UI/API/D1 flow.
- [ ] Purchased items persist across reloads; one felt and one card back equip independently through a single `{ itemId }` API, unaffordable/unowned requests do not overwrite selection, and equipping defaults returns to the original artwork without inserting a default purchase. Authenticated shop and Poker SSR responses carry `private, no-store`; the shop balance updates on **both desktop and mobile**.
- [ ] On cash Poker with 0 chips, browser MCP visually checks the selected **felt** and verifies card-back computed CSS (back stays hidden). On Sit & Go with its independent starting stack, MCP screenshots the **visible** chosen back plus felt. Default/restored paths and guest behavior match originals. Other games and private multiplayer remain unaffected.
- [ ] Desktop and phone screenshots from browser MCP pass visual checks for tiles/buttons, contrast/readability, the shared Art Deco theme and no horizontal overflow. Automated Playwright uses one supported browser/platform; no native acceptance is required.
- [ ] Four existing locales display usable labels and chip prices, test coverage is green, migration/build/lint/type/format checks pass, and evidence is recorded in **the same HPA-731 PR**.
