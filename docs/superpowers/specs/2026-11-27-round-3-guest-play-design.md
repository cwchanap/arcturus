## 1. Poker timing contract

First observe one foreground guest cash hand at the current Normal setting, using browser MCP to distinguish an individual Thinking-to-action interval from several consecutive rivals and the existing 1000 ms street/runout and optional 5000 ms auto-deal pauses. The current rule-based heuristic in `aiEquity.ts` has no simulation loop and guest/SNG never call the LLM; cumulative waiting is a plausible explanation, not a measured fact. **Decision gate:** if a foreground single-rival interval exceeds 2 s (excluding known street/auto-deal pauses and background throttling), reproduce/isolate and fix the actual wait, slow work or misleading turn presentation first, then recheck before retuning. Do not accept a shorter configured timer as a fix for a reproduced multi-second per-action stall. If an actual stall cannot be resolved, record the blocker and keep pacing acceptance open. If intervals already match the published range, proceed directly with the cumulative-pace retune.

**Product decision:** reduce Normal from 800–1500 ms to **600–900 ms** by updating existing `AI_DECISION_DELAY_MIN` / `AI_DECISION_DELAY_MAX` in `src/lib/poker/constants.ts` and using those constants in the Normal/default branch of `GameSettingsManager.getAIDelay` (the existing public minimum export stays consistent), and keep Normal the default; Fast stays 300–600 ms and Slow stays 1500–2500 ms. Existing stored Normal preferences benefit without a migration. Update all four localized speed labels and clarify per-action vs street/hand waits. Do not change rules, strategy RNG, human timer, street/auto-deal delays, or authenticated provider timeout behavior. One focused fake-timer regression should verify exactly one in-range scheduled wait per actionable rival, including successive turns, preserving cancellation/token checks and folded/all-in skipping; existing settings range tests cover all modes. Verify one Normal-speed hand after the change in browser MCP, recording the observed pacing before/after (no fixed wall-clock SLA or production perf instrumentation). Keep existing SNG regressions; use SNG in the UI acceptance for mode pills and tournament separation. Authenticated BYOK provider latency remains outside the local delay range.

## 2. Guest practice chip recovery

Use a common localized **Reset practice chips** action (with amount/this-game-only explanation) visible near the guest bankroll when it is below the existing default 1,000, but enabled only at a safe idle boundary. Explicit click restores the current game's guest balance to exactly 1,000 (not +1,000); normal balances still persist across navigation/reload, no automatic refill. This includes the reported Slots balance 5 even though minimum spin is 1. No reset above the default or while a wager/hand/reveal is in progress. Do not automatically place a bet/deal/spin when resetting. No account credit, settlement, achievements, stats, mission increments, ranked or Daily attempts; no shared guest funds across games.

Centralize the shared operation in `public-game-session.ts`: `canOfferGuestReset(isGuest: boolean, balance: number): boolean` is true only for finite nonnegative guest balances below `DEFAULT_GUEST_GAME_BALANCE`; `resetGuestBankroll(gameKey, userId): number` persists and returns that default using `persistGuestBankroll` (guest-only callers, anonymous namespace). Reuse one common localized action label plus explanatory copy in all four locales. Each game checks its current balance, guest/cash mode and safe phase again at click time; the helper is not a phase or auth authority. Four games already use `createPublicGameSettlementController`: add `resetGuestBalance(localBalance: number)` guarded by the shared eligibility predicate (caller still owns safe phase), using the existing adopt/reset/render callbacks, local baseline and persistence helper. Keep authenticated recovery handler semantics intact; do not call the account gate or dispatch achievement events for a guest reset. The other seven owners use existing setters, render and persist paths. Reset only necessary bankroll/round fields, preserve settings, sound, locale and unrelated keys; storage errors remain best-effort as in existing guest play.

## 3. Result feedback and rival speech

Keep the one pure `winTier` source and inclusive net thresholds from HPA-729 (5/20× resolved stake; poker 20/50 BB). The ticket's 275 gross pot does not establish a qualifying human net gain, and Craps total stake may differ from one Hard 8 bet. Add an actual fixed Craps resolved result (net +250, resolved stake 25 if possible via legal fixture; otherwise record actual stake and use an equivalent qualifying legal fixture) and Poker fixed net result. Existing game integrations are listed in [HPA-729](2026-11-17-big-win-celebration-design.md). Check the reported Craps/Poker seams against their actual net/denominator, keeping other callers and their existing tests unchanged unless a specific regression is discovered. Fire exactly once on visible result, never replayed on hydrate, wallet retry, reset or loss/push. Existing E2E direct module import proves renderer only, not gameplay wiring. Reuse `buildStaticAmount` and `CELEBRATION_MESSAGES.title`: append the existing badge for the big tier unconditionally (instead of only when reduced), add localized title + net amount as separate children with `data-celebration-title` and `data-celebration-amount`, reusing existing huge-tier selectors/formatting (not the huge ribbon geometry). Retain huge ribbon, duration, click-through and reduced motion behavior; only lower thresholds if deterministic results show legitimate ordinary qualifying wins still fail for a measured reason (document a spec amendment rather than quietly widening). No stacking SFX; same mute preference and existing files. Test actual audio invocation with mute/unmute and reduced-motion; acoustic output on headless VM is not required.

For rival talk retain `rivalTalk.ts` event eligibility, priority and no hidden-card information. In existing `tryRivalTalk`, cap non-`replace` (betting) bubbles at one and preserve their 50% roll; skip the probability roll for `replace: true` (only the hand-end caller). Keep total cap two, one active, existing 2.5s display. No selector change. This makes a qualifying result observable while still not reacting to every hand. Reuse existing localized lines and renderer; no extra events based on human losses or false bluff claims. Reuse existing selector tests for rival bad beat, net-big-pot, bluff and SNG elimination; extend quota/roll tests and observe a qualifying hand-end reaction from actual guest gameplay. The playtest's +145 at 10 BB remains below the big-pot threshold by design (unless independently qualifying for a different event); below-threshold, folded and uncalled-return cases do not trigger false reactions. Check portrait overlap, hidden delta behavior and automatic cleanup. Ensure next hand and auto-deal do not leave stale bubbles.

## Risks and delivery

Top risk: Roulette and Craps restore snapshots that can supersede an isolated bankroll write. Mutate through their current session owners; test reload, active bets and the presentation-side busy guard. Secondary risks: Blackjack settings retaining a second balance-write path, Baccarat synchronous resolution and Blackjack unsettled complete phase mistaken for idle, stale poker auto-deal/control state, and guest preview action handlers leaking into shared header. Explicit presentation busy flags and authenticated-only delegated roots avoid the latter regressions; guest helpers never touch account settlement. Keep game-specific safe boundaries and existing API auth tests. One PR; implement in four independently reviewable commit groups with focused Bun tests, lint and typecheck after each. No additional PRs.
