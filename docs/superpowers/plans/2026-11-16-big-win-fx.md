No `src/`, database/API, dependencies, runtime integration, permanent test helpers or extra assets belong in this PR. Keep all intermediate art, WAV masters, generated prompts, scratch previews and screenshots **outside Git**.

## Execution (in this order)

### 1. Generate the five images

- [ ] On the Mac, use Codex image generation requested by Linear (`gpt-6-luna`, `xhigh`) and the existing painted poker artwork as references. Make one top-down, transparent gold chip master; recolor/redraw the red and blue variants with identical silhouette, rim and padding.
- [ ] Create a small four-point gold glint and a wide ribbon **with transparent pixels outside the actual ribbon silhouette**. No text baked into any image; HTML will later supply the four-locale text and count-up.
- [ ] Export WebP to a scratch staging directory: four 128 × 128 sprites plus ~960px-wide ribbon (nominal 960 × 240). Optimize **all five together toward ≤100 KB** without destroying transparency or 24–48px legibility.
- [ ] After the ribbon exists, measure and record the pixel text-safe rectangle `(x, y, width, height)` for HPA-729.

### 2. Generate and master the two sounds

- [ ] Use ElevenLabs on the Mac to make a clean chip cascade (~1.5 s) and an **original** short celebratory sting (~2 s). No speech, licensed melody or long tails.
- [ ] Export 44.1-kHz **mono** MP3 files, each ≤100 KB. Run a single `ffmpeg` `loudnorm` pass toward ~−20 LUFS and isolated ≤−6 dBTP; verify the actual levels with the resulting encode rather than trusting requested filter settings.
- [ ] Mix `coin-shower` and `big-win-sting` starting together (HPA-729 huge tier), check the composite peak **≤−1 dBTP** and audition it. Lower the sources if required; the two individually safe peaks do **not** prove that their sum is safe. Compare the layered result at a similar listening level with the existing poker synthesized `bigWin` cue.

### 3. One-off local measurements (no committed tests)

- [ ] `webpinfo` and Pillow/ImageMagick: WebP encoding, dimensions, alpha/transparency at outside pixels, same chip framing, bytes per image and total.
- [ ] `ffprobe` plus macOS `afinfo`: MP3, mono, 44.1 kHz, durations and bytes; `ffmpeg`: loudness and combined true peak. Check for clipping and a clean end using `afplay` / an automated decoder.
- [ ] Record measurements in the PR. Do not add test packages or a permanent media-validation script.

### 4. **One** temporary preview and automated visual E2E

- [ ] Make a scratch HTML preview **outside the repository**, loading the **staged** seven files and current `public/images/poker/felt.webp`. It is the **same preview** for screenshot evidence and approval; don't build a second Astro page or repeat the preview after committing. Serve the scratch directory via a tiny temporary static server only if `file://` blocks resources.
- [ ] Show chips at native size and 24/32/48px, glint on felt, and ribbon with temporary HTML text and count-up across the four locales. Provide buttons for each MP3 and both **layered**. For a real A/B, use the existing `pokerSound.play('bigWin')` from an ephemeral browser bundle if necessary; do not copy/alter the recipe in the repo.
- [ ] **Browser MCP E2E (one platform suffices)**: load the scratch preview, exercise its display/audio controls, capture screenshots at **1280 × 800** and **375 × 812**, and inspect contrast, transparency, small-chip clarity, ribbon scale and text-safe area against current poker style. Record browser/OS and screenshot links. Run no redundant Astro public-file HTTP 200/decode smoke and no gameplay E2E for an asset-only PR.

### 5. PR preview comment, then final files

- [ ] Post the **single** preview as a PR #89 **Conversation comment**, with both viewport screenshots, individual audio previews and combined playback (attached or accessible temporary links). Ask for a reply **on that comment** to authorize committing the binaries as the Linear ticket requests. If comments cannot carry audio or approval is absent, document the blocker and leave assets staged; do **not** assume that the agent's own screenshots count as approval. The approval is a **workflow precondition**, **not an automated acceptance criterion**.
- [ ] After the preview go-ahead, copy exactly the seven contracted paths into `public/images/fx/` and `public/audio/fx/` on **this branch**. No separate implementation PR and no HPA-729 code.
- [ ] Run `bun run format:check` and `bun run build` **locally on the draft branch**. The existing `.github/workflows/lint.yml` skips the lint job on draft PRs and the build depends on it; do **not** claim draft CI has validated the assets. When marked ready after deliverables, the existing workflow can run as normal.
- [ ] Add sizes, durations, combined audio peak, safe-area coordinates, screenshot evidence, and check results to PR #89. Keep it draft while art/audio are missing.

- [ ] The final PR includes **exactly seven specified binary files and these two docs**, without unrelated source or dependency changes.

- [ ] Browser **MCP** end-to-end checks the one scratch preview on one platform, including both desktop and phone screenshots and audio/visual controls. It verifies small sprite legibility, no rectangular matte, correct ribbon fit and space for localized HTML.
- [ ] `bun run format:check` and `bun run build` pass on the final branch; document actual evidence instead of placeholders.
- [ ] HPA-729 handoff mentions the **existing** synthesized `bigWin` call in `PokerGame.ts`: suppress/route duplicate fanfare on celebrated poker hands while preserving non-celebration feedback, and update `sound.ts`'s header once audio files ship.
